# 1. 프로젝트 개요

## 1.1 프로젝트 목적

본 프로젝트는 OLED/AMOLED 디스플레이에서 발생한 번인, 잔상, 휘도 불균일을 외부 스마트폰 카메라로 측정하고, 그 결과를 기반으로 대상 기기의 화면 출력에 위치별 보정을 적용하여 번인 자국을 시각적으로 완화하는 것을 목표로 한다.

본 시스템은 OLED 픽셀의 물리적 열화를 복구하는 앱이 아니다. 이미 열화된 픽셀을 되살리는 것이 아니라, 상대적으로 덜 열화된 영역의 밝기 또는 색 출력을 제한적으로 낮추어 전체 화면이 더 균일하게 보이도록 만드는 시스템이다.

## 1.2 핵심 아이디어

일반적인 번인 제거 앱은 RGB 화면을 반복 출력하거나 전체 화면을 일정하게 자극하는 방식에 머무른다. 본 프로젝트는 그보다 한 단계 더 나아가 다음 구조를 가진다.

1. 대상 태블릿/폰을 암실 박스 지그 안에 눕히고, 측정 기기를 박스 상판 구멍 위에 카메라가 아래를 향하도록 올려 고정한다.
2. 대상 태블릿/폰에 흰색, 회색, RGB, 마커, 캘리브레이션 패턴을 출력한다.
3. 두 번째 스마트폰 카메라로 대상 화면을 최대 해상도(가능하면 RAW)로 촬영한다.
4. 화면에 표시한 캘리브레이션 패턴으로 카메라 렌즈 왜곡과 비네팅을 추정하고 역산 보정한다.
5. 촬영 이미지에서 화면 프레임(경계)을 인식하고 화면 좌표와 카메라 좌표를 정합한다.
6. 위치별 휘도 저하와 색상 편차를 계산한다.
7. 기기 실제 해상도·화면 비율과 동일한 1:1 보정맵을 생성한다.
8. 대상 기기에서 앱 내부 보정 또는 시스템 오버레이 보정을 적용한다.
9. 보정 후 화면을 다시 측정하여 잔여 오차를 정량 평가하고, 수렴할 때까지 보정맵을 갱신한다.

## 1.3 제품의 본질

본 제품은 “번인 복구 앱”이 아니라 다음에 가깝다.

* OLED 번인 측정기
* 외부 카메라 기반 화면 균일도 분석기
* 네이티브 해상도 위치별 보정맵 생성기
* 앱 내부 또는 시스템 오버레이 기반 시각적 번인 완화 도구
* 저가형 서비스센터식 OLED 보정 실험 플랫폼

## 1.4 주요 차별점

기존 RGB 번쩍임 방식 앱과의 차이점은 다음과 같다.

| 구분            | 일반 번인 제거 앱  | 본 프로젝트          |
| ------------- | ----------- | --------------- |
| 측정 방식         | 측정 없음       | 외부 카메라 측정       |
| 보정 방식         | 전체 화면 자극    | 위치별 보정맵         |
| 보정 단위         | 전체 화면       | 실제 화면 해상도 1:1   |
| 반복 보정         | 없음          | 보정 후 재측정 가능     |
| 아이콘/HUD 자국 대응 | 어려움         | 네이티브 해상도 맵으로 대응 |
| 목표            | 픽셀 자극 또는 착시 | 시각적 균일도 개선      |

# 2. 문제 정의

## 2.1 OLED 번인의 원인

OLED 디스플레이는 각 픽셀이 자체 발광한다. 특정 영역이 오래 밝게 표시되면 해당 영역의 서브픽셀이 더 많이 열화되고, 결과적으로 밝기 저하 또는 색상 편차가 발생한다.

대표적인 번인 원인은 다음과 같다.

* 상태바
* 내비게이션바
* 키보드
* 홈 화면 아이콘
* 게임 HUD
* 고정 로고
* 영상 앱 자막 영역
* 웹 브라우저 상단 바
* 고정 UI 버튼
* 항상 켜져 있는 앱 화면

## 2.2 기존 해결 방식의 한계

기존 방식은 크게 세 가지다.

1. 패널 교체

   * 가장 확실하지만 비용이 높다.

2. 제조사 서비스 보정

   * 일반 사용자가 접근하기 어렵다.
   * 제조사 내부 툴 또는 서비스센터 권한이 필요하다.

3. 번인 제거 앱

   * 대부분 실제 측정 없이 RGB 패턴을 반복 출력한다.
   * 이미 열화된 픽셀을 복구하지 못한다.
   * 위치별 정밀 보정이 불가능하다.

## 2.3 본 프로젝트의 접근

본 프로젝트는 다음 가정을 기반으로 한다.

* 가벼운 OLED 번인은 휘도 차이가 3~5% 수준일 수 있다.
* 이 정도 차이는 정상 영역을 소폭 낮추는 방식으로 상당히 완화할 수 있다.
* 최대 밝기 손실이 5% 내외라면 사용자가 받아들일 가능성이 있다.
* 상태바, 아이콘, 게임 HUD 자국은 저해상도 보정맵보다 네이티브 해상도 보정맵이 유리하다.
* 두 번째 스마트폰 카메라를 측정 장치로 쓰면 저비용으로 번인 맵을 만들 수 있다.

# 3. 제품 목표

## 3.1 1차 목표

1. Android 7.0+ 대상 기기에서 테스트 패턴을 출력한다.
2. 두 번째 Android 스마트폰으로 대상 화면을 촬영한다.
3. 촬영 이미지에서 화면 좌표계를 복원한다.
4. 위치별 휘도/색상 편차를 계산한다.
5. 대상 기기 실제 해상도와 동일한 보정맵을 생성한다.
6. 대상 기기 앱 내부에서 보정맵을 적용한다.
7. 보정 전후 개선 정도를 수치와 이미지로 확인한다.

## 3.2 2차 목표

1. 루팅 없이 시스템 전체 화면 위에 보정 오버레이를 띄운다.
2. 홈 화면, 브라우저, 영상 앱, 게임 등 일반 사용 환경에서도 번인 완화 효과를 제공한다.
3. 오버레이는 터치를 방해하지 않아야 한다.
4. 사용자는 알림바 또는 앱에서 즉시 보정을 끌 수 있어야 한다.

## 3.3 3차 목표

1. RGB 채널별 보정맵을 생성한다.
2. 밝기 단계별 보정 프로파일을 생성한다.
3. 보정 후 재측정을 반복하여 오차를 줄인다.
4. 상태바, 아이콘, 게임 HUD처럼 고주파 번인 영역을 정밀 보정한다.
5. 루팅/커스텀 ROM 환경에서 시스템 합성 레벨 보정을 실험한다.

## 3.4 최종 지향점

본 프로젝트는 제조사 서비스툴처럼 한두 번 보정하고 끝내는 수준을 목표로 하지 않는다. 최종 지향점은 다음이다.

* 측정 → 보정 → 재측정 → 평가 루프를 잔여 오차가 수렴할 때까지 반복한다.
* 보정 후 잔여 휘도 편차를 일반 시청 거리에서 지각 한계(JND) 이하로 낮추는 것을 이상적 목표로 한다.
* 암실 지그로 측정 조건을 고정하여, 세션 간 측정 재현성을 확보한다.
* 카메라라는 저가 측정기의 한계(렌즈 왜곡, 비네팅, 노이즈)를 캘리브레이션과 역산으로 최대한 제거한다.
* 매 세션의 평가 결과를 리포트로 남겨 "얼마나 좋아졌는지"를 수치로 증명한다.

즉, "조금 완화" 수준이 아니라 **회색 화면에서 번인 자국이 식별되지 않는 수준**을 명시적 목표치로 두고, 그 목표에 도달했는지 평가 단계에서 판정한다.

# 6. 제품 형태

## 6.1 앱 구성

제품은 최소 2개의 Android 앱으로 구성된다.

### 6.1.1 대상 기기 앱

번인이 있는 태블릿 또는 스마트폰에 설치한다.

역할:

* 테스트 패턴 출력
* 마커 출력
* 보정맵 수신
* 보정맵 적용
* 오버레이 보정
* 프로파일 관리
* 보정 전후 비교

### 6.1.2 측정 기기 앱

두 번째 스마트폰에 설치한다.

역할:

* 대상 화면 촬영
* 수동 카메라 제어
* 마커 검출
* 좌표 정합
* 휘도/색상 맵 계산
* 보정맵 생성
* 대상 기기로 전송
* 결과 리포트 생성

## 6.2 측정 지그: 암실 박스

측정 정확도와 재현성을 위해 소프트웨어 외에 간단한 물리 지그를 표준 측정 환경으로 정의한다.

### 6.2.1 구성

```text
┌─────────────────────────┐
│  [측정 기기]  ← 박스 상판 위에 눕혀 거치, 카메라가 구멍을 통해 아래를 향함
│ ────●──────  ← 상판 카메라 구멍 (카메라 렌즈 위치)
│                         │
│        (암실 내부)        │   내부는 무광 검정 (반사 억제)
│                         │
│  [대상 기기, 화면 위로]     │  ← 박스 바닥에 눕혀 배치
└─────────────────────────┘
```

* 박스: 종이 박스, 하드보드 등 빛을 차단할 수 있는 재질이면 충분하다.
* 상판에 카메라 렌즈용 구멍을 뚫고, 측정 기기를 상판 위에 눕혀 카메라가 구멍과 일치하도록 거치한다.
* 대상 기기는 박스 바닥에 화면이 위를 향하도록 눕힌다.
* 내부는 가능하면 무광 검정 처리하여 화면 빛의 내부 반사를 줄인다.

### 6.2.2 지그가 해결하는 문제

| 문제 | 지그 없는 경우 | 지그 사용 시 |
| --- | --- | --- |
| 주변광 | 측정마다 달라짐 | 차단됨 |
| 화면 반사 | 조명·창문 반사 발생 | 억제됨 |
| 카메라-화면 거리/각도 | 손으로 들면 매번 다름 | 고정됨 |
| 흔들림 | 손떨림으로 프레임 편차 | 없음 |
| 반복 측정 재현성 | 낮음 | 높음 → 반복 보정 수렴 가능 |
| 보정 전후 비교 | 조건이 달라 비교 불가 | 동일 조건 비교 가능 |

특히 반복 보정(측정→보정→재측정)은 측정 조건이 고정되어야 수렴하므로, 지그는 반복 보정의 전제 조건이다.

### 6.2.3 촬영 거리 요구

카메라와 화면 사이 거리는 다음을 만족해야 한다.

* 화면 전체가 카메라 프레임 안에 여유 있게 들어올 것 (프레임의 70~90% 권장)
* 카메라 최소 초점 거리보다 멀 것
* 화면 1픽셀이 카메라 센서에서 가능한 여러 픽셀로 샘플링되도록 가까울 것

앱은 카메라 정렬 화면에서 현재 거리·기울기·프레임 점유율이 적절한지 실시간 판정하고, "박스를 더 높게/낮게" 안내를 제공해야 한다.

### 6.2.4 소프트웨어 요구

* 앱은 지그 사용을 전제로 한 "암실 모드"를 기본 측정 모드로 제공한다.
* 암실 모드에서는 검정 패턴 촬영값으로 잔여 미광(迷光)을 검증하고, 기준 초과 시 차광 보완을 안내한다.
* 지그 없이 측정하는 "간이 모드"도 허용하되, 정확도가 낮음을 경고하고 confidence를 낮게 책정한다.
* 측정 도중 프레임 내 화면 위치가 변하면(기기 밀림) 측정을 중단하고 재정렬을 안내한다.

## 6.3 개발 보조 도구

초기 개발 단계에서는 PC 분석 도구를 제공한다.

역할:

* 수동 촬영 이미지 분석
* OpenCV 기반 좌표 정합
* 보정맵 생성
* 보정 전후 이미지 비교
* 알고리즘 디버깅
* JSON/PNG 결과 출력

PC 도구는 제품 최종 구조의 필수 구성요소가 아니라 개발 검증용이다.

# 7. 핵심 사용자 흐름

## 7.1 첫 실행 흐름

1. 사용자가 대상 기기 앱을 실행한다.
2. 앱이 프로젝트의 한계를 안내한다.

   * 물리 복구가 아님
   * 최대 밝기 손실 가능
   * 심한 번인은 완전히 숨길 수 없음
3. 사용자가 “새 측정 시작”을 누른다.
4. 앱이 측정 준비 체크리스트를 보여준다.
5. 사용자는 측정 기기 앱을 실행한다.
6. 두 기기가 QR 코드 또는 로컬 네트워크로 페어링된다.

## 7.2 측정 흐름

1. 사용자가 대상 기기를 암실 박스에 넣고, 측정 기기를 상판 구멍 위에 거치한다.
2. 측정 기기 앱이 정렬 화면에서 거리·기울기·프레임 점유율을 실시간 판정한다.
3. 대상 기기 앱이 캘리브레이션 패턴(체커보드/도트 그리드)을 표시하고, 측정 기기 앱이 렌즈 왜곡 계수를 추정한다.
4. 대상 기기 앱이 균일 회색 패턴을 표시하고, 측정 기기 앱이 플랫필드(비네팅) 프로파일을 추정한다.
5. 대상 기기 앱이 검정 패턴을 표시하고, 측정 기기 앱이 black offset과 잔여 미광을 검증한다.
6. 대상 기기 앱이 마커 패턴을 표시하고, 측정 기기 앱이 화면 경계(프레임)와 마커를 인식하여 화면 비율·해상도를 확인한다.
7. 대상 기기 앱이 회색/RGB 패턴을 순차적으로 표시한다.
8. 측정 기기 앱이 각 패턴을 최대 해상도로 여러 장 촬영한다.
9. 측정 기기 앱이 왜곡 역산 → 플랫필드 보정 → 좌표 정합 순으로 촬영 이미지를 화면 좌표계로 변환한다.
10. 위치별 휘도/색상 편차를 계산한다.
11. 번인 맵과 confidence map을 생성한다.

## 7.3 보정 흐름

1. 측정 기기 앱이 보정맵을 생성한다.
2. 대상 기기 앱이 보정맵을 수신한다.
3. 대상 기기 앱이 보정 전후 미리보기를 보여준다.
4. 사용자가 보정 강도를 선택한다.
5. 사용자가 앱 내부 보정 또는 시스템 오버레이 보정을 적용한다.
6. 측정 기기 앱이 보정 후 화면을 다시 촬영한다.
7. 잔여 오차를 계산하여 평가 지표(잔여 편차, 균일도 점수)와 합격 여부를 표시한다.
8. 미달이면 보정맵을 갱신하고 6~7을 수렴할 때까지 반복한다.
9. 최종 평가 리포트를 저장한다.

## 7.4 실사용 흐름

1. 사용자가 시스템 오버레이를 켠다.
2. 앱이 알림바에 상시 제어 버튼을 표시한다.
3. 사용자는 홈 화면, 브라우저, 영상 앱 등에서 보정 효과를 확인한다.
4. 특정 앱에서 문제가 생기면 앱별 예외 설정을 한다.
5. 언제든 알림바에서 보정을 끈다.

# 9. 보정 원리

## 9.1 기본 보정 개념

특정 위치의 실제 밝기 능력을 `measured(x, y)`라고 하고, 목표 균일 밝기를 `target`이라고 한다.

이론상 보정값은 다음과 같다.

```text
gain(x, y) = target / measured(x, y)
```

하지만 일반 앱 권한에서는 실제로 번인된 영역을 더 밝게 만드는 것이 어렵고, OLED 수명에도 좋지 않다. 따라서 기본 정책은 다음이다.

```text
정상 영역을 낮춘다.
번인 영역은 가능한 그대로 둔다.
전체 화면을 번인 영역에 맞춰 균일하게 만든다.
```

## 9.2 보정값 범위

기본 보정맵 값은 다음 의미를 가진다.

```text
1.00 = 보정 없음
0.99 = 해당 위치를 1% 낮춤
0.97 = 해당 위치를 3% 낮춤
0.95 = 해당 위치를 5% 낮춤
0.90 = 해당 위치를 10% 낮춤
```

기본 모드는 5% 이내 보정을 권장한다.
10% 이상 보정은 실험 모드로 분리한다.

## 9.3 네이티브 해상도 보정

최종 보정맵은 대상 기기 실제 해상도와 동일해야 한다.

예시:

```text
1920 × 1080 화면 → 1920 × 1080 보정맵
2560 × 1600 화면 → 2560 × 1600 보정맵
2800 × 1752 화면 → 2800 × 1752 보정맵
2960 × 1848 화면 → 2960 × 1848 보정맵
```

이유:

* 상태바 자국은 픽셀 위치가 고정적이다.
* 내비게이션바 자국은 경계가 뚜렷하다.
* 게임 HUD는 작은 아이콘 단위로 남을 수 있다.
* 홈 화면 아이콘 번인은 저해상도 맵으로 보정하면 퍼져 보일 수 있다.
* 키보드 자국은 경계와 반복 패턴이 중요하다.

## 9.4 측정 해상도와 보정 해상도의 분리

보정맵은 네이티브 해상도로 저장하지만, 카메라가 실제로 모든 픽셀을 정확히 측정할 수 있다는 뜻은 아니다.

따라서 내부적으로는 다음을 분리한다.

```text
촬영 해상도: 카메라 원본 이미지 해상도
분석 해상도: 신뢰 가능한 휘도 측정 해상도
보정맵 해상도: 대상 기기 실제 해상도
렌더링 해상도: 대상 기기 실제 해상도
```

보정맵은 네이티브 해상도로 만들되, confidence map을 함께 생성하여 신뢰도 낮은 영역에서 과보정하지 않도록 한다.

## 9.5 Confidence Map

각 픽셀 또는 영역의 측정 신뢰도를 나타내는 맵이다.

값의 의미:

```text
1.0 = 직접 측정 신뢰도 높음
0.7 = 대체로 신뢰 가능
0.5 = 보간 또는 smoothing 기반 추정
0.2 = 신뢰 낮음
0.0 = 적용 금지
```

보정 적용 시 confidence가 낮은 영역은 보정 강도를 줄인다.

예시:

```text
finalCorrection = correction * confidence + neutral * (1 - confidence)
```

## 9.6 고주파 번인

고주파 번인은 작은 아이콘, 글자, 상태바, 게임 HUD처럼 경계가 뚜렷한 번인을 의미한다.

고주파 번인 대응 요구:

* 네이티브 해상도 보정맵 사용
* 마커 기반 정밀 좌표 정합
* 화면 회전 상태별 별도 프로파일
* edge-preserving smoothing
* 과도한 Gaussian blur 금지
* 보정 전후 확대 비교 제공

* 태블릿/폰 모두 대응

대상 기기 앱은 전체 화면으로 테스트 패턴을 표시해야 한다.

필수 패턴:

* 검정
* 흰색 70%
* 흰색 85%
* 회색 30%
* 회색 50%
* 회색 70%
* 회색 85%
* 빨강 70%
* 초록 70%
* 파랑 70%
* 마커 패턴
* 격자 패턴

주의:

* 100% 흰색은 카메라 클리핑과 OLED ABL 때문에 기본 측정 패턴으로 사용하지 않는다.
* 70~85% 밝기 회색을 기본 측정 패턴으로 사용한다.

### T-FR-003. 마커 패턴 표시

카메라 좌표와 화면 좌표를 맞추기 위한 마커를 표시해야 한다.

* 격자점
* 해상도 정보 코드
* 패턴 ID 코드

마커는 측정 중 자동으로 표시되며, 측정 기기 앱이 현재 패턴과 방향을 인식할 수 있어야 한다.

### T-FR-004. 전체 화면 고정

### M-FR-015. 카메라 렌즈 왜곡 감지 및 역산 보정

측정 기기 앱은 측정 세션마다 카메라 렌즈 왜곡을 추정하고 역산 보정해야 한다. 스마트폰 카메라는 배럴/핀쿠션 왜곡이 있어, 왜곡을 무시하면 화면 가장자리에서 좌표 정합이 수 픽셀 이상 어긋나 고주파 번인 보정이 불가능해진다.

캘리브레이션 방식:

* 대상 기기 화면 자체에 체커보드 또는 도트 그리드 캘리브레이션 패턴을 표시한다. 별도의 인쇄물 없이 화면이 곧 캘리브레이션 타깃이 된다.
* 화면에 표시된 그리드의 실제 픽셀 좌표는 정확히 알려져 있으므로, 검출된 그리드 점과 비교하여 카메라 내부 파라미터와 왜곡 계수를 추정한다.
* 왜곡 모델: 방사 왜곡 k1, k2, (k3), 접선 왜곡 p1, p2 (OpenCV 표준 모델)
* 지그에 고정된 단일 시점이므로 완전한 intrinsics 추정이 어려울 수 있다. 이 경우 homography + 잔여 왜곡 필드(격자 보간) 방식으로 근사한다.

요구사항:

* 왜곡 추정 후 재투영 오차(reprojection error)를 계산하고 리포트에 기록한다.
* 재투영 오차가 임계값(기본 1.0 카메라 픽셀)을 초과하면 사용자에게 재정렬을 안내한다.
* 추정된 왜곡 계수는 측정 기기+거치 조건 조합으로 캐시하되, 지그 재배치가 감지되면 재추정한다.
* 모든 측정 이미지는 왜곡 역산(undistort)을 적용한 뒤 정합·분석에 사용한다.
* 왜곡 보정 전/후 격자 오버레이 시각화를 고급 모드에서 제공한다.

### M-FR-016. 플랫필드(비네팅) 캘리브레이션

카메라 렌즈 비네팅과 센서 lens shading은 화면 가장자리를 실제보다 어둡게 측정하게 하여, 가장자리 과보정이라는 최악의 오류를 유발한다. 측정 기기 앱은 이를 보정해야 한다.

방식:

* 대상 화면에 균일 회색 패턴을 표시하고 촬영하여 저주파 감쇠 프로파일을 추정한다.
* 단, 화면 자체 불균일(번인 포함)과 렌즈 비네팅이 섞여 있으므로 다음으로 분리한다.
  * 비네팅은 렌즈 광축 중심의 부드러운 방사형 함수라는 사전 지식으로 모델 피팅한다 (cos⁴ 근사 또는 저차 다항식).
  * 카메라를 지그 위에서 소폭 이동/회전한 2회 이상 촬영을 비교하면, 카메라에 붙어 움직이는 성분(비네팅)과 화면에 고정된 성분(번인)을 분리할 수 있다. 이 절차는 정밀 모드에서 제공한다.
* RAW 촬영 시 센서의 lens shading map 메타데이터가 있으면 활용한다.

요구사항:

* 기본 측정 파이프라인에 플랫필드 보정 단계를 필수 포함한다.
* 플랫필드 분리 신뢰도가 낮은 영역(모서리 등)은 confidence를 낮춘다.
* 플랫필드 프로파일도 왜곡 계수와 함께 세션 캐시에 저장한다.

### M-FR-017. 보정 적용 후 평가

측정 기기 앱은 보정맵 적용 후 재측정하여 보정 품질을 정량 평가하고 합격/미달을 판정해야 한다. "적용했더니 좋아 보인다"가 아니라 수치로 판정하는 것이 본 프로젝트의 차별점이다.

평가 절차:

1. 보정 적용 상태에서 기본 측정 패턴(회색 70% 등)을 재촬영한다.
2. 보정 전과 동일한 파이프라인(왜곡 역산 → 플랫필드 → 정합)으로 휘도 맵을 생성한다.
3. 보정 전 맵과 화면 좌표계에서 1:1 비교한다.

평가 지표:

* 잔여 RMS 편차 (전체 화면)
* 잔여 P95/최대 편차
* 영역별(9분할 등) 편차
* 번인 마스크 영역의 잔여 대비 (자국이 얼마나 남았는가)
* 고주파 잔여 성분 (작은 자국 잔존 여부)
* 개선율 = 1 − (after RMS / before RMS)
* 지불 비용 = 평균 밝기 손실

판정:

* 합격 기준(기본값): 잔여 RMS 편차 1.5% 이하 그리고 번인 마스크 잔여 대비 시각 임계 이하
* 합격 시: 프로파일을 "검증됨"으로 표시하고 최종 리포트를 저장한다.
* 미달 시: 반복 보정 계속 또는 "이 번인은 카메라 측정 한계로 더 개선 불가" 판정을 사유와 함께 제시한다.

## 13.2 보정맵 값


```text
attenuation = pixelValue / 255 * maxAttenuation * userStrength
```


값 의미:

# 14. 알고리즘 요구사항

## 14.1 촬영 전처리

필수 처리:

* black offset 제거
* lens shading 보정
* exposure consistency check
* white balance consistency check
* blur detection
* overexposure detection
* underexposure detection
* reflection warning

## 14.2 카메라 캘리브레이션 및 왜곡 역산

측정 이미지는 분석 전에 반드시 다음 순서의 기하·광학 보정을 거친다.

```text
원본 촬영 이미지
  → 1. black offset 제거
  → 2. linearization (RAW이면 생략 가능)
  → 3. 렌즈 왜곡 역산 (undistort, k1/k2/k3/p1/p2)
  → 4. 플랫필드(비네팅) 보정
  → 5. homography 기반 perspective warp
  → 6. 격자 기반 잔여 국소 왜곡 보정 (정밀 모드)
  → 화면 좌표계 정렬 이미지
```

원칙:

* 왜곡 계수는 화면에 표시한 체커보드/도트 그리드로 세션마다 추정한다 (M-FR-015).
* 순서를 지킨다. 왜곡 역산 전에 homography를 확정하면 가장자리 정합이 틀어진다.
* 각 단계의 잔여 오차(재투영 오차, 정합 오차)를 수치로 남기고 confidence에 반영한다.
* 재투영 오차 목표: 1.0 카메라 픽셀 이하. 이는 대상 화면 기준 약 1~3 화면 픽셀 정합 정확도에 해당하며, 고주파 번인 보정의 전제 조건이다.

## 14.3 화면 정합

필수 처리:

* screen boundary detection
* marker detection
* homography estimation
* perspective correction
* orientation normalization
* native coordinate mapping
* 화면 비율/해상도 교차 검증 (마커의 해상도 ID와 검출된 경계 비율 비교)

## 14.4 휘도 계산

기본 휘도 계산은 linear RGB 기준으로 수행한다.

절차:

1. 카메라 RGB 값을 linear space로 변환
2. black offset 제거
3. luminance 계산
4. 위치별 평균 또는 중앙값 계산
5. 정상 기준 영역 추정
6. 상대 휘도 편차 계산

## 14.5 보정 목표값 결정

보정 목표값은 화면 전체의 최저값에 맞추면 과도하게 어두워질 수 있다.

따라서 기본 목표값은 다음 중 하나로 정한다.

* 하위 5~10 percentile
* 사용자가 지정한 최대 밝기 손실 기준
* 번인 영역 마스크 기반 기준값
* 보정 제한값 기준 자동 계산

기본값:

```text
target = 하위 10 percentile 휘도값
maxAttenuation = 0.05
```

## 14.6 보정맵 생성

기본 정책:

```text
정상 영역을 낮춤
번인 영역은 유지
1.00 초과 gain 금지
```

보정값:

```text
rawGain = target / measured
clampedGain = clamp(rawGain, 1.0 - maxAttenuation, 1.0)
```

단, 오버레이 방식에서는 gain map이 아니라 alpha attenuation map으로 변환한다.

## 14.7 네이티브 해상도 확장

측정값은 카메라 해상도와 신뢰도에 따라 제한되므로, 보정맵 생성 과정은 다음을 따른다.

1. 분석 가능한 해상도로 휘도 맵 생성
2. 고주파 후보 영역 분리
3. 저주파 얼룩 영역 smoothing
4. 고주파 번인 영역 edge-preserving 처리
5. 네이티브 해상도로 upsample
6. confidence map 적용
7. 값 범위 제한
8. 최종 보정맵 저장

## 14.8 고주파 번인 처리

작은 UI 자국은 다음 정책으로 처리한다.

* 위치 정합 오차가 작을 때만 적용
* confidence가 낮으면 보정 강도 제한
* edge-preserving smoothing 사용
* Gaussian blur 과도 적용 금지
* 확대 비교에서 사용자 확인 후 적용 가능
* 최대 보정값은 기본값보다 낮게 제한

## 14.9 반복 보정

반복 보정은 고정 횟수가 아니라 수렴 기반으로 동작한다. 암실 지그로 측정 조건이 고정되어 있으므로, 오차가 줄어드는 한 반복을 계속할 수 있다.

반복 보정 공식:

```text
newCorrection = oldCorrection * pow(target / measuredAfter, alpha)
```

기본값:

```text
alpha = 0.3            (초기값, 수렴 속도에 따라 0.1~0.5 적응 조정)
stopThreshold = 0.005  (반복당 개선량이 0.5% 미만이면 수렴 판정)
maxIterations = 10     (기본 모드 안전 상한)
maxIterations = 30     (고급 모드, 사용자 명시 동의 시)
```

중지 조건:

* 개선량이 stopThreshold 미만 (수렴)
* 평가 지표가 합격 기준 도달 (M-FR-017)
* 오차 증가 2회 연속 (발산 → 마지막 개선 시점 맵으로 롤백)
* 과보정 감지
* 카메라 조건 변화 (노출/정렬 변동 감지)
* 사용자 중지

수렴 후에도 미달이면, 남은 오차의 원인(측정 한계 / 보정 한계 / 번인 심도)을 분류하여 리포트에 기록한다.

## 14.10 보정 품질 평가

보정 적용 후 평가는 M-FR-017의 지표를 사용하며, 알고리즘 관점의 요구는 다음과 같다.

* 보정 전/후 측정은 반드시 동일 파이프라인, 동일 캘리브레이션 계수로 처리하여 비교 가능성을 보장한다.
* 평가 맵은 화면 좌표계에서 픽셀 단위로 정렬된 상태에서 계산한다.
* 저주파(얼룩)와 고주파(자국) 잔여 성분을 분리 평가한다. 저주파는 개선됐지만 고주파 자국이 남은 경우를 구분해야 한다.
* 개선율, 잔여 RMS, P95, 번인 마스크 잔여 대비, 평균 밝기 손실을 표준 지표 세트로 고정하여 세션 간 비교가 가능하게 한다.

# 26. 최종 요약

본 프로젝트는 Android 7.0 이상 기기에서 동작하는 OLED 번인 측정·보정 시스템이다.

핵심은 다음과 같다.

1. 대상 기기와 측정 기기를 암실 박스 지그에 고정하여 측정 조건을 통제한다.
2. 번인된 대상 기기에 테스트 패턴과 캘리브레이션 패턴을 띄운다.
3. 두 번째 스마트폰 카메라로 화면을 최대 해상도(가능하면 RAW)로 측정한다.
4. 화면에 표시한 캘리브레이션 패턴으로 렌즈 왜곡을 추정·역산하고 비네팅을 보정한다.
5. 마커를 이용해 카메라 좌표와 화면 좌표를 맞춘다.
6. 휘도/색상 저하 지도를 만든다.
7. 대상 기기 실제 해상도와 동일한 보정맵을 생성한다.
8. 앱 내부 또는 시스템 오버레이로 정상 영역을 소폭 낮춘다.
9. 보정 후 다시 측정하여 잔여 오차를 정량 평가하고, 합격 기준에 수렴할 때까지 반복한다.

가벼운 번인, 특히 3~5% 수준의 휘도 차이는 충분히 완화 가능성이 있다.
상태바, 홈 화면 아이콘, 게임 HUD, 키보드 자국처럼 위치가 고정된 번인은 네이티브 해상도 보정맵을 사용해야 정밀하게 다룰 수 있다.

초기 개발은 PC/OpenCV 기반 오프라인 검증에서 시작하고, 이후 Android 측정 앱, 대상 기기 앱, 시스템 오버레이, 반복 보정 순서로 확장한다.

본 제품은 OLED를 물리적으로 복구하는 것이 아니라, 화면 출력의 위치별 밝기와 색을 조정하여 사람이 보는 번인 자국을 줄이는 **외부 카메라 기반 OLED 균일도 보정 시스템**이다.
